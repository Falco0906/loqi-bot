GLOBAL TRANSPORT / AUTH CONTRACT
• Legacy web-session family (/api/web/session/...): HTTP middleware requires Authorization: Bearer <identity access token or web-session bearer>; path {session_token} is explicitly ignored as a credential. Missing/invalid credentials return {"detail": string}, 401. The creation bootstrap POST /api/web/session is excluded.
• Selected workspace: X-Workspace-Id is optional client input, independently membership-authorized. Multi-workspace/no selection can return 409; legacy owner default fallback remains in _resolved_workspace_id_or_default, so this is an explicit compatibility exception, not universal strict workspace selection.
• Identity routers: Authorization: Bearer opaque identity access-session token, with 401 {"detail": string}; OAuth callbacks use query parameters/state; Stripe webhook uses Stripe-Signature; Telegram webhook authenticity is not evident at route decorator level.
• Request headers observed: Authorization; X-Workspace-Id; X-Timezone (briefing); Stripe-Signature; standard OAuth callback query code/state. No cookie auth is accepted by identity dependency.
• Generic FastAPI validation errors are 422 with detail array. Explicit HTTPException usually serializes as {"detail": string}; unhandled exceptions are framework 500 (shape not explicitly frozen by application).

CONTRADICTIONS / UNDOCUMENTED BEHAVIOR TO PRESERVE UNTIL EXPLICITLY CHANGED
1. /health is declared twice: main.py and services/operations/router.py. Router inclusion occurs after middleware but before direct declaration; FastAPI route order determines which is served. Both currently return {status:"healthy"}, but duplicate registration makes ownership/observability ambiguous. UNCLEAR/CONTRADICTORY.
2. Onboarding is production bearer-protected but deliberately accepts bare user_id in development when no Authorization header is supplied. This is an environment-dependent external contract.
3. Legacy session routes all carry {session_token} but middleware ignores it and reads Authorization. Both path shape and header requirement are externally observable.
4. Many legacy route success schemas are bare dicts while frontend depends on particular keys; route source does not declare response_model. They are IMPLEMENTED but untyped, so implementation is the only current contract.
5. Identity OAuth and separate Gmail OAuth endpoints coexist with different persistence/session semantics. They cannot be considered one interchangeable contract.
6. _resolved_workspace_id_or_default retains an owner-default fallback for legacy/fixture accounts. This conflicts with strict selected-workspace semantics and must remain recorded as a compatibility rule until removed through an explicit contract change.
